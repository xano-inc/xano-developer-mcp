# Workspace policies

Requires a platform build with policy support. A policy is its human description plus deterministic rules, saved as branch-scoped workspace XanoScript. Checks inspect stored definitions; nothing runs at request time. This topic is the one reference for the policy language: its syntax, fields, rules, refusal messages and versioning. The Metadata API and CLI `policy` topics cover the routes and commands.

## Quick Reference

```xs
policy "AUTH-EXAMPLE" {
  title = "Require authentication"
  statement = "Endpoints require authentication unless the endpoint or its API group is tagged public."
  severity = "high"
  active = true
  enforcement = "advisory"

  rule {
    check = "object.auth_required"
    params = {except_tags: ["public", "xano:quick-start"]}
  }
}
```

That block is the parser's own output, byte for byte. The key is written quoted, `policy "AUTH-EXAMPLE" {`, which is the form the platform emits in canonical source (parse results, `source` on a read, `workspace pull`). An unquoted key of letters, digits, `.`, `_` and `-` parses too, but write the quoted form so your source matches what comes back. Canonical source also fixes the field order (`title`, `statement`, `severity`, `active`, `enforcement`, then a blank line before the first rule) and the spacing of a `params` map: a map with one key stays inline with no padding inside the braces, `params = {except_tags: ["public"]}`, and a map with several keys is written one key per line with the colons aligned. Write what you like and let `policy parse` format it; do not hand-tune spacing to match.

**A policy file carries no comments.** A comment inside a policy block is refused outright, whether it sits on its own line or trails a value. `//` and `/* */` both get the same sentence, naming the line they are on:

```
line 3: policy files cannot contain "//" comments. Put the explanation in the policy's statement, rationale or narrative.
```

with `"/* */"` in place of `"//"` for a block comment. For a trailing comment — `severity = "high" // critical | high` — the message names that line and the position points at the comment, not at the value. `#` is a plain syntax error: `Syntax error: unexpected '#'`. Never annotate policy source; put the explanation in `statement`, `rationale`, `narrative` or a rule's `title`.

`enforcement` decides what a finding does. An active `blocking` policy's findings block: they refuse a merge, a set-live, a publish or push to the live branch, and a tenant deploy of a release that has them (see Gates). `advisory` findings are reported and block nothing, and a policy save itself is never gated. An inactive policy (`active = false`) is never evaluated by a branch run; an active one is. **Write a new policy `active = true` with `enforcement = "advisory"`**, the pair a policy that omits both lines gets. It blocks nothing while its findings are reviewed, and, unlike an inactive policy, it is actually evaluated, so the author can see what it reports. Use `active = false` only to park a policy you do not want evaluated at all. Policies can also include `rationale`, `narrative` and `tags`. There is no `owner` field: canonical source never writes one, and every authored path — source parse, dashboard save, Metadata API save and `workspace push` — refuses an `owner` line or key with `policy: "owner" was removed; delete the line. Ownership will return as a reference to a workspace member.` (on the source path the refusal also carries the line and column). There is no `remediation` field either, on a policy or on a rule: it is refused with `policy: "remediation" was removed; put the guidance in the policy statement.` (on a rule the sentence is prefixed by the rule's position instead of `policy:`). Long text such as `narrative` can use a `"""` triple-quoted multiline string. `tags` is a list of strings, for example `tags = ["soc2", "hipaa"]`, the same syntax as tags on any other workspace object; there is no separate framework/mapping concept, a tag is simply how a customer labels a framework.

`severity` says how much a violation of this policy matters. It orders findings in reports, and it never blocks a gate — enforcement does. Its four values are `critical`, `high`, `medium` and `low`; nothing else is accepted. It defaults to `medium`, and canonical source omits the line at that default. `active` and `enforcement` are always written, because they are what decide whether a policy blocks.

Each rule selects a built-in check and supplies literal parameters:

- **A rule cannot be named.** Only `rule { ... }` is legal; `rule foo { ... }` is refused with `A rule cannot be named. Write "rule {" — rules are identified by position (KEY.R1, KEY.R2…).` A rule takes the id `<KEY>.R<n>` from its position, so the first rule of `AUTH-EXAMPLE` is `AUTH-EXAMPLE.R1`. The same goes for the JSON form: a custom `rules[].id` is refused with that sentence, and an echoed `<KEY>.R<n>` is ignored and re-derived. To give a rule a human name, set its `title`.
- On an existing policy, keep the order of existing rules and add new rules at the end: stored runs cite rule ids, and ids follow position.
- A rule `title` is optional. An unnamed rule is displayed by its check's label — author title, else check label, else rule id, everywhere the platform names a rule. Title a rule only where its scoping makes the check's own label misleading.
- **A rule has no `severity`.** Both surfaces refuse it and say the same thing, prefixed by the rule's position: `"severity" is set on the policy, not on a rule.` Every finding carries its policy's severity.
- `params` lists only what the rule sets. Every omitted parameter takes the catalogue default, and canonical source drops any value equal to that default, so a rule that configures nothing has no `params` line. The stored document stays fully expanded, so a read's `rules[].params` lists every parameter while its `source` stays sparse. The `source` every read serves is canonical, so it can be sent back unchanged (a no-op) or edited.

`guard` and `test` blocks are reserved and refused, even when empty: `Policy block "<name>" is reserved. Policies support rule blocks only.`

## Authoring workflow

1. Read the branch's existing policies and the instance's check catalogue. The catalogue is the only source of truth for what each check reports, which object kinds it inspects and the exact parameters it accepts.
2. Write one `policy KEY { ... }` document in `policies/KEY.xs`, from scratch or from a template (below). Customize its key, statement and rules. The file name is the key: Studio refuses to publish a policy file named otherwise (`This file declares policy KEY, and a policy file is named after its key: rename it to /policies/KEY.xs.`). Change a key only when the user asks, renaming the file to the new key with it; never move a policy to a file named anything else.
3. Validate and format through the native `POST /api:meta/workspace/{id}/policy/parse` endpoint with `{source}` (and `branch`, to be warned against that branch). The result contains `{policy, source, rule_warnings}` and writes nothing; `rule_warnings` lists each rule that would do nothing or allow too much there. Read them before saving. With the authenticated Xano MCP, use its policy parse tool. The developer MCP's `xano_validate_xanoscript` checks a policy file locally first: syntax and block-shape problems (comments, a named rule, a field set twice, a non-literal parameter) are errors, and what the check catalogue decides (an unknown check, field or parameter, a value outside its set, a removed field) is a warning, checked against the catalogue the language server ships with, which can be older than your instance. A local pass is a preview; the instance's parse decides.
4. Save canonical source using `POST /policy` (create) or `PUT /policy/{id}` (update) with `{branch, data: {source}}`. Do not combine source with structured fields. **To change an existing policy, update it by its id** — read the id from the policy list (`xano_list_policies`, `xano policy list -o json`), take the `source` a read returns, edit it, and send it to `PUT /policy/{id}` (the authenticated MCP's save tool with `policy_id`). This is also how an inactive policy becomes active: the same policy id, with `active = true` in the source. A `POST` whose key already exists is refused, naming the policy that holds it — `A policy with key "AUTH-001" already exists on this branch (policy id 12, "Authentication baseline"). To change it, update policy id 12 instead of creating a new one.` — and a `PUT` whose source carries another policy's key says which id is which. Both are HTTP 400 with `payload.code` `policy_key_taken`, `key` (the key sent), `existing_key` (the holder's, which differs only in case when the sent key does) and `existing_id` (null when a concurrent create took the key first); branch on the code, not the sentence. A create whose rules exactly match a live policy on the branch is refused too, with HTTP 400 `payload.code` `policy_duplicate`: `A policy with exactly these rules already exists: KEY. Change a parameter or scope to add another.`, and `existing_key`, `existing_id` and `policies` (each copy as `{key, existing_key, existing_id}`). The rules are compared as a set of checks with their normalized params (scope fields are params); the key, title, statement, severity, enforcement, `active`, tags and rule titles are ignored. Only a create is refused, never an update, and a push refuses its copies before anything is imported. The `source` a read returns is canonical, so it is safe to send back unchanged (a no-op) or edited. Add an optional `message` (and `description`) to label the Version History entry the save creates. The server owns versioning: see below.
5. Evaluate the same branch and read its verdict and findings. A run is evidence only for the definitions it checked: every policy a read serves carries `latest_run`, the platform's answer to whether the branch's newest run still describes it (`stale: true` once the policy changed after that run, `included: false` when the run did not evaluate it). A run snapshots the policies it checked: each policy's `statement` as written at run time and, per rule, its display `label` and the resolved `params` the check actually ran with (values that resolved to nothing are omitted, and an empty map serializes as `[]`). `xano policy status --run-detail` prints them. A run can hold tens of thousands of findings, so read a large one in parts: its summary (counts, each policy's verdict, each rule's finding count) and its findings a page at a time, filtered by blocking, policy, rule, severity, object kind, object, tag or text (`GET …/policy/run/{run_id}/summary` and `…/findings`; `xano policy runs <id>` with `--offset`, `--limit` and filter flags; the authenticated MCP's run tool). An evaluation can answer that summary with its first 50 findings (`answer: "summary"`, `xano policy evaluate --summary`, and the MCP evaluate tool, which always asks for it), and the `policy_check` a push answers lists the first 100 findings beside `counts`, `total` and `truncated`: the stored run (`run_id`) has them all. A pusher without `workspace:policy` read is evaluated the same way (the run is stored) but told only their own findings on the objects the push carried (see Permissions).

Policies also travel in the platform's workspace multidoc import/export. Use the official CLI's `workspace pull` and `workspace push` flow for a local workspace (the CLI `workspace` topic covers `push -m`). The authenticated MCP supports workspace exports and one-time upload URLs for large multidocs; upload processes the source on the instance. On a branch that is not live, a blocking finding reported after a push does not roll back that import; a push to the live branch is gated before it commits (see Gates).

Inside Xano's own agent, the instance serves a platform skill named `xano-policies`, generated from the live check catalogue: this file format, every check id and its parameters, and the authoring rules. A coding agent installs the terminal variant of the same skill with `xano skills pull` (see the CLI `skills` topic).

## Starting from a template

The check catalogue response (`GET /api:meta/workspace/{id}/policy/check`) also carries `templates`: the platform's list of starting points for a policy, such as "Endpoints require login". Each template holds what a policy needs to be created from it: `id`, `category` (the id of the group it is filed under; the response's `template_categories` lists the groups in the order to offer them, each as `{id, label}`: `access_control` Access control, `data_protection` Data protection, `secrets` Secrets, `integrations` Integrations, `reliability` Reliability, `testing` Testing; groups cut across object kinds and are not compliance frameworks), `title` (the new policy's `title`), `summary` (its `statement`), a suggested `key`, the policy `severity`, search `keywords`, a one-sentence `limits` note on what its rules cannot see, and `rules[]` of `{title, check, params, needs, needs_any}`. `params` are sparse, and `needs` names the parameter paths the author must fill; a need is never seeded. Every `needs` path is required unless the rule says `needs_any: true`, when one filled path is enough (the vendor allowlist takes hosts, providers or both); `needs_any` is false on every other rule.

In the dashboard, **Create Policy** opens the templates (**Start from scratch** is in its ▾ menu), grouped by category, with a search over each template's title, summary, category and keywords and over its rules' titles and their checks' ids, labels, keywords and first description sentence. **Choose** on a template opens the create form with its title, statement, key, severity and rules filled in, leaving only the `needs` to fill; nothing is saved or run until the author saves, and that first save starts Run Checks, unless the policy is inactive, a run is already in flight or the author may not run checks. The same form edits a policy after creation (**Edit Policy**). In the form a rule is edited in place: a row click, **Clone** or **Add Rule** opens the rule view in the same panel ("← Back to <policy>", **Cancel** / **Apply**); **Apply** puts the rule into the form, and only the form's **Save** stores the policy. On the policy page, a Rules row click, **Edit Rule**, **Clone Rule** and **Add Rule** open the rule panel directly, and its **Save** stores the policy; **Delete Rule** confirms, then saves the policy directly. A clone is named with the lowest free number ("Require auth 2"), and a rule's name is a field in its form. Every save is the ordinary whole-policy save. A template can be used more than once: a key the branch already uses gets a `-2`, `-3`… suffix, and a copy whose rules exactly match a policy the branch has is refused (`policy_duplicate`, see Authoring workflow) until a parameter or scope changes. **Add Rule** searches the checks. To author from a template yourself, find the matching one, copy its rules into `policies/KEY.xs`, fill every `needs` path (at least one of them for a `needs_any` rule) from the check's catalogue schema, and parse; with the CLI, `xano policy create --template <id>` does the same. A policy created from a template is ordinary: active and advisory, with no record of the template.

Each template also carries `frameworks`: framework tag ids, possibly none, from the response's `template_frameworks` (`[{id, label}]`, in the order to offer them: `soc2` SOC 2, `hipaa` HIPAA, `gdpr` GDPR). A tag marks a template on a topic that framework also covers (access control, audit logging, sensitive or personal data, secrets, data in transit, vendors, change testing). It is a second way to find templates, not a mapping to a framework's criteria: a tag never means that the template, or a policy made from it, makes a workspace compliant, and Xano does not track changes to the frameworks. The response's `template_frameworks_note` is the platform's sentence saying so; show it wherever the tags appear. The dashboard's template search also matches each tag's id and label, and `xano policy catalogue` ends each template row with its tags in brackets. A policy created from a tagged template carries no framework tag. To label a policy with a framework, add the tag to its `tags` yourself (`tags = ["soc2"]`), and never say the policy satisfies the framework.

## Versioning

Policies version exactly like every other Xano object: one Version History entry per real change, with the author, the optional `message` and `description`, and the whole policy as it was.

- `version` on a policy is the index of its newest history entry. It moves only when the definition really changes, so it names an entry a reader can open rather than counting writes.
- A save whose definition matches the stored one **does nothing at all** — no new version, no `updated_at`, no history entry, no audit record — and the response carries `unchanged: true`. A real save carries `unchanged: false`. Re-sending identical source is therefore safe and cheap; do not "touch" a policy to force a version.
- Formatting is not content: sending the same definition as expanded source, or as sparse canonical source, is the same no-op.
- An existing policy gets a lazy `Baseline` entry at its current number the first time it is really edited, so numbers are never migrated or renumbered.
- An update or a delete can send the `updated_at` it last read; when the policy changed since, it is refused (`payload.code` `policy_stale`) with `A previous update was performed before your request. Please reload your data and try again.` and nothing changes. Read the policy again, then reapply the edit or delete again.
- Listing, diffing and restoring versions is a **dashboard** surface. The Metadata API has no version routes — for policies or for any other object type — so an API or MCP client can label a save but cannot read or restore history. A restore performed in the dashboard is an ordinary save: it moves `version` forward rather than rewinding it, and re-validates against today's check catalogue.
- A run's snapshot records the `version` it evaluated, and each policy's `latest_run.stale` says whether that is still the current version. Read `stale`; do not compare versions or timestamps yourself.

## Gates

Blocking policies gate changes, not saves. One rule decides every branch gate (the tenant deploy gate judges a release on its own; see Releases and tenants):

- **Which policies decide:** the active blocking policies the branch will have after the change: its policies with the change's own selected policy changes applied (a new policy added, an updated one replaced, a deleted one removed). A merge counts the policies it carries (`select.policy`), a push to the live branch its policy files, and a set-live the candidate branch's policies, which are what live will have (a branch that landed no policy, such as one an `import-schema` created, is judged by the live branch's policies instead). So a merge that relaxes a policy (an exemption, a narrowed scope) and adds an object relying on it passes, and a merge that adds a blocking policy and an object violating it is refused. The branch before the change is judged by the same policies, so a new policy's findings on objects the change leaves alone are existing debt. A change that leaves the branch with no active blocking policy is never evaluated by a gate; one that adds the branch's first is. An archive import with `mode=merge` counts none of the archive's policies: the branch's policies before the import decide, and policies the archive writes take effect once it has landed.
- **Weakening a blocking policy:** a merge, push or set-live that weakens a policy that is active and blocking on the branch before the change (demotes, deactivates or deletes it, removes a rule, narrows a scope, adds an exemption or loosens a parameter) needs `workspace:policy` **update**, from a session that may write, as an override does. For a set-live, a live blocking policy the candidate branch lacks counts as deleted, unless the candidate landed no policy at all, which is not checked for weakening. If the set-live check cannot read the policies it fails closed: only a caller with update proceeds, and anyone else is refused with the same code, `unavailable: true`, no policies named and `Set live refused: whether it weakens a blocking policy could not be checked, and weakening one needs the workspace:policy update permission. The live branch was not changed.` Otherwise the change is refused before anything is written: HTTP 403 with `payload.code` `policy_weakening_permission_required`, `gate`, `permission` (`workspace:policy`), `level` (`update`) and `policies` (the keys), and the message `<Gate> refused: it weakens blocking policy KEY, which needs the workspace:policy update permission. <outcome>`, for example `Push refused: it weakens blocking policy GATE-001, which needs the workspace:policy update permission. Nothing was imported.` (a merge ends `Leave the policies out of the merge to merge the rest.`, a set-live `The live branch was not changed.`). A caller who holds update in a session that may not write reads `… permission from a session that may write.` A release deploy with set live adds what landed first (`The release was deployed as branch "<label>". `) and names it in `payload.branch`. `override_reason` does not lift it. The merge dry run and its policy plan report it without refusing, as `weakening {policies, permission, level, allowed}`; the push dry run refuses the same way. A set-live that goes through with such a weakening writes a `policy_run:set_live_weakened` audit row naming the policies and how each was weakened.
- **Deleting a blocking policy** needs `workspace:policy` **update** as well as delete, on every branch: `Delete refused: it weakens blocking policy GATE-001, which needs the workspace:policy update permission.` (`payload.gate` `delete`). Deleting an advisory or inactive policy needs only delete. An archive import that deletes existing policies (`mode=replace`, or `mode=merge` with `delete=true`) is refused the same way when it would remove an active blocking policy of the branch it writes that the archive does not bring back: `Archive import refused: it weakens blocking policy GATE-001, which needs the workspace:policy update permission. Nothing was imported.` Because a carried policy change counts, editing a policy is never part of a fix (see Fixing a finding).
- **What blocks:** blocking findings the change **introduces**, and blocking findings on objects whose definition it **changes**. Findings already on unchanged objects are existing debt: reported as `existing`, never blocking.
- **Refusal:** HTTP 403 with `payload.code` `policy_gate`, the message `<Gate> refused: N blocking policy finding(s) from KEY (X introduced by this change, Y on objects it changes).` (it names the policies the blocking findings come from, the first three, then `and M more`, to every caller, policy read or not), and `{gate, status, total, introduced, changed, existing, run_id, can_override, sources, findings, truncated}`; `findings` (the first 100) only for a caller with `workspace:policy` read. Every gate answer (a merge's and its dry run's `policy_gate`, the merge review, set-live, the tenant deploy gate, a refusal's payload) carries `sources`, the same list as the message (`from AUTH-010 and PII-001`), to every caller whenever its blocking findings name a policy. Nothing is written.
- **Override:** a caller holding `workspace:policy` **update** may proceed by giving a reason (`override_reason`), which writes a `policy_run:override` audit row. Never override on a user's behalf unless they gave you the reason.
- An engine fault fails open (`unavailable`); a permission failure is a refusal. A rule that cannot run on an active blocking policy makes the branch gates `unavailable`, and the change goes through ungated until every rule can run; a rule error on an advisory or inactive policy changes no branch gate.

| Gate | When | How to override |
| --- | --- | --- |
| Merge | Every branch merge (Studio). Its dry run shows the verdict first | `override_reason` |
| Set live | Making a branch live, judged by that branch's own policies (what live will have) and measured against the current live branch. A release deployed into its workspace with `set_live`, and a Metadata API `import-schema` with `setlive`, land a new branch first: a refusal keeps it and names it in `payload.branch` (`{id, label}`). A new branch that landed no policy (`import-schema` always leaves the archive's policies out; a release may carry none) is judged by the live branch's policies; a release deploy that lands the release's policies is judged by them | `override_reason`; `xano branch set_live` and `xano release deploy --set_live` take `--policy-override "<reason>"` |
| Archive import | `mode=merge` through the Metadata API | `override_reason` |
| Publish | A save of a draftable object (function, query, task, middleware, addon, tool, workflow test, trigger, realtime message), an agent, an MCP server or a realtime channel to the workspace's **live** branch only (Studio publish and saves, Metadata API creates and saves, beta publish). Other branches are not gated | Studio's override dialog; `override_reason` on the Metadata API create and save routes; `xano function create` and `xano function edit` take `--policy-override "<reason>"` |
| Push | A non-draft `workspace push` to the live branch; it needs its transaction (`policy_gate_transaction_required` otherwise) | `override_reason` on the multidoc and upload routes; `xano workspace push --policy-override "<reason>"` |
| Tenant deploy | Deploying a release to a standard or run tenant: any blocking finding in the release's own check refuses it, existing debt included (see Releases and tenants) | `override_policy` with the reason |

A push to a branch that is not live is not gated: it imports, then answers `policy_check`, and a blocking finding does not roll it back. Tables, API groups, environment variables, workspace and branch settings, realtime servers, and MCP prompts and resources are saved without the publish gate, although a check may read one (a realtime server's middleware): a blocking policy never refuses those saves, on the live branch too. The next run reports what they break, and a set-live or tenant deploy that carries it is gated. No check reads an MCP prompt or resource; adding one to an MCP server or removing it changes the server, so that save is gated.

## Plan limits

Lower plans cap the policies on each branch, active or not; Pro and above are unlimited. A create past the cap is refused with HTTP 403 `payload.code` `policy_plan_limit` (`plan`, `plan_name`, `limit`, `count`, `adding`, and `policies` on a push); the message names the plan and says to upgrade. A branch already over its cap keeps, edits, deactivates, demotes and deletes its policies. A push whose new policies do not fit is refused whole before any write; an archive import skips the new ones that do not fit and lists them in `policies_skipped`. Never work around a plan limit (for example by deleting or merging policies the user did not ask you to touch): tell the user.

## Releases and tenants

Policies travel where the code travels while the instance's `policies` feature is on:

- A **branch merge** carries policies like other objects: added, changed and deleted. A merge that changes a policy needs `workspace:policy` create, update or delete for what it changes and obeys the plan cap; the carried policies count toward the merge's own gate (see Gates), and the merge review lists each one with its diff and calls out weakening. With the feature on, the merge review (Studio's dry run of the merge) gives a member without `workspace:policy` read the gate's verdict trimmed instead: the counts and `sources` for every blocking finding, their own blocking findings on objects they may read (trimmed, first 100, `access: "coverage"`; a trigger by its `obj_type` as the dry run left it, one that cannot be resolved needing every trigger scope; each with the check and fix hint of the policies the merge leaves) and a fixed `note`, never the policy plan, with a merge error about policies read as one fixed sentence (a key clash, or a target policy changed meanwhile, keeps its own sentence, which names only keys); the merge itself is gated for them as for anyone. Such a member may ask for 20 merge reviews a minute in a workspace; past that the review is refused with 429 `policy_merge_review_rate_limited` and `retry_after`, before anything is exported, and Studio says `Too many merge reviews in the last minute, so the policy check wasn’t previewed. Check again in a moment.` without holding Merge. A reader's review is not limited.
- A **release** carries its branch's policies (inactive ones included) and records a policy check when it is cut (`GET /workspace/{id}/release/{release_id}/policy_run`, `xano policy runs --release <name>`). A release built from files by `release push` carries its policy files only for a caller holding `workspace:policy` create and update; for anyone else it carries the workspace's live-branch policies instead (see Permissions). **Deploying** a release makes the tenant's policies exactly the release's, and is gated by the release alone: the blocking findings of the release's own policy check (the one stored when it was cut, or checked from its archive on demand) refuse the deploy unless overridden, existing debt included. A rule that could not run does not lift that refusal; a release with no blocking finding whose check has a rule that could not run (on any policy) is `unavailable`, and the deploy is not gated. The gate does not compare the release with what the tenant runs, so the same release gets the same verdict on every tenant. Its answer is `{gate, status, total, run_id, can_override, sources?, gated, release {id, name, run_id, status, counts, carried}, message, findings, truncated}` (`GET /workspace/{id}/tenant/{tenant_name}/policy_gate?release_name=`, `xano tenant deploy_release --check`); `findings` and `truncated` go only to a caller with `workspace:policy` read, while the `message` names the blocking policies to everyone (`Deploy blocked: this release has 1 blocking policy finding from AUTH-001.`). Both preview routes need `workspace:policy` read, so only a reader calls them. A blocked deploy's refusal (the deploy and approve routes) tells a caller without policy read the counts, `sources` and the sentence naming the policies, never the findings. An approval request's stored `deploy_error` is that refusal's own sentence, with the policies named (and the override-denied suffix when it applies); no finding is stored. Ephemeral and sandbox tenants get the verdict (`gated: false`) and are never refused, and a release cut before releases carried policies is `not_carried` and not gated. Deploying a release into a workspace as a new branch lands its policies there.
- A **tier1 tenant, ephemeral or sandbox push** and its dry run carry policy documents without authoring permission or plan cap. A remote tenant push, and a push to a tenant created before policies (it has no policy table until its next platform update), still leave them out and name them once in `policies_skipped` (`{message, keys}`), whose message says why.
- A backup restore, a workspace archive and a branch clone carry every policy on the branch (inactive policies included) with its `guid` and `version`; runs and Version History do not travel. Those copies keep the fields the receiving platform knows and drop the rest, and a policy that still cannot be read (for example a check an older platform does not have) is skipped with a `policy:import_skipped` warning in the audit log, naming the policy and the reason, while everything else imports. Authored writes (Metadata API, Studio, `workspace push`) stay strict.

While the feature is off nothing carries policies: exports, clones and Git sync leave them out, and an import (a push, an archive import, including replace and delete) leaves the incoming policies out with a note, never creates or updates a policy, and deletes only the policies of a branch a replace removes, as deleting that branch would.

## Check catalogue

A rule selects one built-in check and supplies literal parameters. Unknown check IDs and parameter names are rejected on parse and save; an unknown check id is refused with `payload.code` `policy_unknown_check` and the nearest ids. A check id that was renamed is refused the same way with the sentence `"query.auth_required" was renamed to "object.auth_required"; use the new id.` and the new id in `payload.renamed_to`; a renamed or removed parameter is refused with a sentence naming what replaced it (for example `"statement" was renamed to "statements" and takes a list`). ## Scoping a rule

Scope selects the objects a check reports on. Every scope field is a top-level rule parameter with one spelling; there is no nested `scope` object, and a `scope = {...}` parameter is refused with `"scope" was removed; use the top-level ...`. All set fields must match; omitted or empty fields add no restriction. A check may still read objects outside its scope (auth tables across the branch, called functions, tests, the middleware chain); each check's description says what it reads beyond scope.

<!-- BEGIN GENERATED: scope -->
Scope limits what is reported, not what is read.

- `tags` (string[]) — Include only objects carrying any listed exact tag. Uses the object's own tags, not the tags of tables it reads; endpoints also carry their API group's tags.
- `api_groups` (string[]) — Endpoints in these API groups, matched by exact display or canonical name. Selects endpoints only: every other object kind is excluded.
- `tables` (string[]) — Tables by exact name, or objects reaching a named table directly or through called functions, attached addons and enabled agent or MCP tool mappings. db.direct_query reaches a table its static SQL names physically (mvpw<workspace>_<table id>).
- `verbs` (string[]) — Endpoints with these HTTP verbs, matched case-insensitively. Selects endpoints only: every other object kind is excluded.
- `endpoint_auth` (string) — Endpoints only, from the endpoint's own authentication setting: required selects endpoints that require authentication, none selects public endpoints. Any other object kind is excluded; empty adds no restriction. One of `""`, `none`, `required`.
- `except_tags` (string[]) — Exclude objects with any listed exact tag; this wins over every other scope field. Endpoints also carry their API group's tags. Empty adds no exclusions.
- `object_kinds` (string[]) — Include only these object kinds, from those the check inspects. Empty keeps every kind the check supports. One of `table`, `query`, `function`, `workflow_test`, `api_group`, `task`, `trigger`, `middleware`, `addon`, `channel`, `message`, `tool`, `agent`, `mcp_server`, `workspace`.
- `reaching_table_tags` (string[]) — Include only objects reaching a table carrying any listed exact tag, directly or through called functions, attached addons and enabled agent or MCP tool mappings; db.direct_query reaches a table its static SQL names physically. The table's own tags.
<!-- END GENERATED: scope -->

`api_groups`, `verbs` and `endpoint_auth` select endpoints only and exclude every other object kind. On a check that also inspects other kinds, setting one of them without `object_kinds: ["query"]` draws a rule warning (`api_groups only matches endpoints, so this rule inspects endpoints only; set object_kinds: ["query"] to say so.`); say so explicitly. A scope field that cannot change what a check selects (for example `verbs` on a table check) is refused on save; the catalogue's per-check `scope_fields` lists the fields that apply, with `applies_when` where that depends on another parameter's value.

Xano already records whether an endpoint is public (its authentication setting), so never add a tag just to restate that. Use `endpoint_auth: "required"` to keep a rule to endpoints that require authentication (test coverage, required middleware), and `endpoint_auth: "none"` to state what public endpoints may not do, e.g. `stack.statement_forbidden` with `statements: ["db.edit", "db.del"]`. `object.auth_required` has no parameters of its own: a deliberately public endpoint is an ordinary exception, `except_tags: ["public"]`, on the endpoint or on its API group.

Prefer tags to names. A rule scoped with `tags` or `except_tags` keeps working when an API group or table is renamed, and a new object opts in by carrying the tag; a rule scoped with `api_groups` or `tables` must be edited whenever those names change. A name the branch does not have selects nothing: the run reports it as a warning on the rule's result (`warnings`) without changing the result's status.

Example, in the canonical spelling the parser returns:

```xs
    params = {
      statements  : ["db.add", "db.edit"]
      verbs       : ["GET"]
      except_tags : ["generated"]
      object_kinds: ["query"]
    }
```

## Writing parameter values

- **Types:** `string[]` is a list of strings; `bool` requires true or false. `number` accepts finite numeric literals, not numeric strings. Both `min_count` parameters are `integer` with minimum 1. Bounds are inclusive and use the checked parameter's native units; `unit` only labels findings.
- **Object values:** use objects such as `{}` for selectors and maps. The catalogue publishes object defaults as `{}`. `value` in `table.field_attribute_required` accepts any literal, including null.
- **Statement names:** use an exact XanoScript name such as `db.add` or `api.request`; stored aliases such as `mvp:dbo_add` also work. A misspelled name is accepted on save and matches nothing, so the rule inspects no statements and passes (or, for a required-statement check, fails everywhere). Verify the name against statement documentation, then evaluate and read the rule result's `warnings`: a name that is not a XanoScript statement is reported there as `Statement "db.edt" is not a XanoScript statement name, so it matches nothing. Did you mean db.edit?` A stored alias containing `:` is compared as written and is never warned about.
- **Parameter paths:** use a name or dotted path such as `data.role`. Aliases include `per_page` for paging size, `where` for search conditions and `error` for the error message.
- **References:** match a reference or its child paths. `$auth` matches `$auth.id`; `$input.id` does not match `$input.id2`. Supported roots are `$input`, `$auth`, `$env`, `$var`, `$error` and `$output`. Quoted text is literal.
- **Literal comparison:** false differs from "false", and 0 differs from "0". Equal numbers match, including 1 and 1.0. Empty objects and lists share a stored representation and compare equally. This applies to forbidden literals, field attributes and setting equality.
- **Names:** table, function, middleware, tag, field and provider names match exactly. Hosts and HTTP verbs ignore case; a host written with a leading dot (`.example.com`) approves that domain and its subdomains. Regex is not supported, and neither are wildcards, except that `stack.statement_forbidden` accepts a trailing `.*` to forbid a statement namespace (`db.external.*`); every other check refuses one on save. Credential `patterns` selects built-in shapes.
- **Combined conditions:** field names and field types must match the same field; table selectors combine all conditions. Allowed write functions and tags are alternatives. `object.input_rules` needs an enabled condition and `statement.containment` needs a structural constraint. `statement.expression_rule` fails an omitted parameter only when the rule sets `must_reference` or `filters_required`.
- **Tags:** `tags` and `except_tags` match the inspected object's own tags; an endpoint also carries the tags of its API group. `reaching_table_tags`, `table_tags` (`object.tagged_table_access`, `db.output_fields_forbidden`, `statement.param_required`) and `db.where_constraint_required`'s `table_selector.tag` match table tags, and check parameters such as `allowed_tags` read only the object's own tags.
- **Lists, not single values:** checks that name statements, params, functions or tables take lists (`statements`, `param_names`, `functions`, `restricted_tables`, `names`, `field_types`); any listed entry matches. A list whose default is the built-in set (`literal.credential_shape.patterns`, `outbound.vendor_allowlist.kinds`, `table.write_location_restricted.statements`, `db.write_from_input_forbidden.statements`) stores `[]` for "every built-in, including ones added later"; a listed subset stays that subset.

## Findings

A finding carries `policy_key`, `policy_title`, `rule_id`, `rule_title`, `severity`, an `object` reference and a `message` saying what was found and where in the stack. A `literal.credential_shape` finding also carries `allow: {allowed_secrets: ["sha256:<64 hex>", ...]}`, the full fingerprints of the secrets it reports (its message names them short); no other check sets `allow`. Findings arrive in one order: blocking first, then by severity, policy key, rule position (R2 before R10) and object. `rule_title` is the rule's own title, else its check's label, else its id; `severity` is the owning policy's, so every finding of one policy shares it. A finding `id` is prefixed with the policy key when the rule id does not already name it, so two policies whose rules share an id still produce distinct findings. Guidance that applies to the whole policy, such as how to request an exemption, belongs in the policy `statement`. Some catalogue entries carry an optional static `fix_hint` string describing the usual fix for that check; it is the same for every rule that uses the check.

<!-- BEGIN GENERATED: fix-hints -->
- `db.output_fields_forbidden`: Remove the field from the statement's output list, or list the output explicitly without it, and say what callers stop receiving. When the object must read it (to verify a password, say), the rule does not fit that object: exempting it is the policy owner's decision, not a fix.
- `literal.credential_shape`: Use a workspace environment variable ($env) instead of the literal; the user sets its value and rotates the exposed one, never you in a file. Never quote any part of the value, even a prefix. A value already in an environment variable is in place: change nothing, and leave narrowing the rule's locations to the owner. Allowing a value by its fingerprint (allowed_secrets) is the owner's call; never add one.
- `object.auth_required`: Enabling auth changes who can call the endpoint or handler: ask first, naming the auth table you would use. If it is deliberately public (login, signup, webhook, health), exempting it (the policy's except_tags) is the policy owner's decision: propose it, never apply it.
- `object.input_rules`: An input read only through whole $input is still used; do not delete it. Without input_names, filter rules reach every text input and the unused rule every input; set input_names to target inputs, one rule per group. Keep an input declared only for API docs by exempting the object or leaving unused_forbidden off.
- `object.middleware_required`: Attaching per object replaces inherited middleware; prefer the API group, channel or branch default, and ask.
- `outbound.vendor_allowlist`: Approving a vendor is the policy owner's decision: report the host and ask, or ask the owner to approve the env var in env_hosts. Never add it to the allowlist yourself, and never replace a dynamic URL with a literal.

- `table.auth_table_rules`: Which table is the auth table is the owner's decision: ask before changing table or endpoint auth to clear this. Several intentional auth tables belong in auth_tables.
- `table.coverage_required`: A placeholder object satisfies the check, not the policy; ask what it must do. Never rename an existing object to match a name the rule lists.

A rule with `checked: 0` and no findings has status **`no_objects`** and message `no objects checked`. Older stored runs keep `pass` with `checked: 0`; readers accept both as no objects checked. The run and `policy_check` stay `pass` when nothing failed, and `policy_check.message` names the unchecked rules. The CLI and Studio show no objects checked, which proves nothing about coverage: it says the rule's scope matched no objects, not that anything satisfied the rule. Treat it as a question about the scope: widen it until it reaches the objects the `statement` is about, or confirm that matching nothing on this branch is intended. Merge, publish and deploy gates still read findings, so `no_objects` does not block them.

### Fixing a finding

Read the policy before editing anything: its `statement`, and the failed rule's check, params and scope. A finding is one line about one object; whether the rule was meant to reach that object is only answerable from the rule. A fix changes the object the finding names, and every change it could make is in one of three classes. A check's `fix_hint` adds detail to this rule and never overrides it.

- **Do it** once the user has asked for a fix: the change the failed rule asks for, on the object the finding names, that leaves who may call it and every table and its data as they are. Add the required statement or call, constrain a read or write by a field that exists, make a flag or parameter explicit, drop the forbidden field from what a statement returns, replace a literal secret with an `$env` reference, add the unit test the rule asks for (the only extra object a fix may create). Then say what changed, object by object, and what a caller now sees differently.
- **Ask first**, showing the exact change: enabling or changing an endpoint's auth or auth table (it changes who can call it; a login, signup or webhook is often public on purpose), adding, renaming, retyping or deleting a table or field, writing or deleting data, activating, deactivating or rescheduling a task or trigger, creating an object other than the required unit test, adding or removing a tag (tags decide which policies apply), removing behaviour, or touching an object the findings do not name. Ask too when the rule names a field, table or tag the object does not have, or tests something the `statement` never asks for: the policy is then probably scoped too wide (an empty selector or scope means everything) or lacks an exemption.
- **Never, in a fix:** edit the policy; add a tag that a policy's `except_tags` or `allowed_tags` lists, an allowlist entry or an `allowed_secrets` fingerprint; rename, delete or retype a table or field to match a rule (tables are shared by every branch); invent a GUID, schema or value; work around a plan limit. When only one of these would clear a finding, leave it: that is the policy owner's decision. Offer it last among the options, labelled so.

Fix at most three objects before checking back with the user, blocking findings first. Never quote any part of a secret in a reply, not even a prefix. Never weaken a rule silently, and never infer an intent the `statement` does not state. In a non-interactive run, make only the first class of change and report the rest.

### An object's coverage and draft checks

In the dashboard, an object's page shows a **Policies** chip and panel: the active policies that apply to it and why, and its findings in the branch's newest run (`Policies ✓ 6 pass`, `Policies 2 blocking · 1 advisory`, `3 apply · not checked yet`, `Last check failed`, `None apply`). A member without `workspace:policy` read who may read the object sees it too, trimmed: each applying policy's key, title, Blocking or Advisory and why it applies, the passing ones included, and each finding's policy key, rule name, message and the check's fix hint (opened: the check's label and the first sentence of its description). It leaves out statements, rule settings and warnings, links to the policy and its reports, and other objects' findings, and ends with a muted note that full details need `workspace:policy` read. The same trimmed answer is served on the Metadata API (`GET /workspace/{id}/policy/object/coverage?type=&id=&branch=`), by `xano policy coverage <type>:<id>` and by the authenticated MCP's `xano_get_policy_coverage` (the workspace object's id is the workspace's own id: `workspace:17`); it needs only the object kind's own read permission (see Permissions). The answer is the same for every caller and is cached for 60 seconds by object, the branch's latest run and the workspace's checksum with the policies' fingerprint, so a write, a policy change or a new run is never answered from the cache. Without policy read the rule and its statement cannot be read, so fix from the message and fix hint, and ask the policy's owner when the rule's intent matters.

While an object has a draft, Studio checks that draft alone, laid over the published branch, when the XanoScript editor saves it or when **Check draft** in the chip or panel is pressed; it does not check on page open (`Draft not checked`). The draft's result replaces the published one, labelled Draft, with New and Fixed markers, a count of the findings it introduces on other objects (linked for policy readers, a count only for anyone else) and, on the live branch, whether publishing it would be refused. Only a member who may edit the object (its kind's update permission, as Save asks) has its draft checked. A draft check stores nothing (no run, report or audit row), runs in its own small pool and answers busy when every slot is taken (check again in a moment); a slot's lease is renewed between rules while its check runs, so a check of a large branch keeps its slot, and a worker that dies frees it within a minute. Each member may ask for 20 draft checks a minute in a workspace (past that, 429 `policy_draft_check_rate_limited` with `retry_after`, which Studio also shows as busy), and a draft is at most 1 MiB as JSON (400 `policy_draft_too_large`; Studio says `This draft is too large to check.` without sending it). It is Studio-only: the Metadata API, the CLI and the MCP have no draft check, so outside Studio evaluate after the change is saved or pushed.

## Following policies while you change code

Policies are not only for policy work. When the branch has **active** policies (files under `policies/`, or a non-empty `xano_list_policies` / `xano policy list`), every code change should keep to the active **blocking** ones — their findings refuse a merge, a publish or push to the live branch, and a tenant deploy — and ideally to the advisory ones too:

1. Before writing code, read the active policies that apply to what you are changing (their `statement` and rules).
2. Write code that meets them. A rule you cannot meet is a question for the user, not something to route around (see above: never exempt the object yourself).
3. After changing code, evaluate the branch and read what the change introduced: `xano policy evaluate` (exit 2 means a blocking finding), the `policy_check` that `xano workspace push` returns, or the authenticated MCP's `xano_evaluate_policies`. Report only what the evaluation printed.

The generated `xano-policies` skill carries the same instructions for the surface it is pulled for.

## Permissions

Every policy request passes the same gates. A refusal is an HTTP 403, and its `payload.code` names the gate, so a client keys on the code rather than on the wording:

| Gate | Passes when | `payload.code` | Refusal message |
| --- | --- | --- | --- |
| Feature | The instance has the `policies` feature enabled | `policy_feature_disabled` | `Policies are not enabled on this instance.` |
| Role permission | The caller's role (or its override on this workspace) grants `workspace:policy` at the level the operation needs | `policy_permission_required` | `The workspace:policy <level> permission is required on this workspace.` |
| Token scope | A Metadata API access token was created with that `workspace:policy` level | `policy_scope_required` | `This API token was not granted the workspace:policy <level> scope.` |
| Writable session | A write (create, update, restore, delete) comes from a session that may write: not a read-only Studio session or a read-only impersonation | none | `This is a read-only session. Enable editing to modify this resource.` |
| OAuth ceiling | An OAuth token carries `workspace:read` (reads) or `workspace:write` (writes) | none | `insufficient_scope: workspace:read` or `workspace:write` |

One route family is the exception: an object's coverage (`policy/object/coverage`, both APIs) and Studio's draft check need the object kind's own permission instead of `workspace:policy`, **read** for coverage and **update** for the draft check, since someone who may not edit an object has no draft of it (`workspace:api` for an endpoint or API group, `workspace:function`, `workspace:database` for a table, `workspace:task`, `workspace:middleware`, `workspace:addon`, `workspace:workflow_test`, `workspace:tool` for tools, agents and MCP servers, `workspace:realtime` for channels and messages, `workspace:settings` for the workspace; a trigger's by what it is attached to, its `obj_type`: `workspace:database` for a table trigger, `workspace:tool` for an agent or MCP server trigger, `workspace:realtime` for a realtime trigger, `instance:workspace` for a workspace or error trigger and for a trigger the branch does not hold, and all four for one whose `obj_type` cannot be resolved; a trigger the caller may not use is answered exactly as one the branch does not hold, refused naming `instance:workspace` or a 404 to a caller who holds it, so its existence never shows), behind the same feature gate and OAuth `workspace:read` ceiling, which is checked first. Its refusal is `policy_object_permission_required` (403, with `permission`, `level` (`read` or `update`) and `type`): `Reading this function needs the workspace:function read permission.`, or for a draft check `Checking a draft of this function needs the workspace:function update permission.`

Both coded permission refusals also carry `permission` (`workspace:policy`) and `level`. A refused push lists the policy files it would have written in `payload.policies`, and its message ends `; nothing was imported: KEY, KEY`. The remedy follows the code: `policy_permission_required` needs an instance admin to grant the role's Workspace Policies permission (a new token does not help); `policy_scope_required` needs a token created with the level.

The `workspace:policy` permission level each operation needs:

| Operation | `workspace:policy` level | OAuth ceiling |
| --- | --- | --- |
| List, get, check catalogue, policies for an object, runs, one run (whole, its summary or its findings pages), parse | `read` | `workspace:read` |
| Evaluate (run checks) | `read` | `workspace:read` |
| One object's coverage (`policy/object/coverage`) | none: the object kind's own read permission | `workspace:read` |
| Studio's draft check | none: the object kind's own update permission | `workspace:read` |
| Create a policy | `create` | `workspace:write` |
| Update a policy, restore a version | `update` | `workspace:write` |
| Delete a policy | `delete`, and `update` as well for an active blocking policy | `workspace:write` |
| `workspace pull` / export with policies included | `read` (without it the export still succeeds and omits policies) | `workspace:read` |
| `workspace push` / import of a policy file that differs from the stored policy | `create` or `update`, and `update` for a push to the live branch that weakens a blocking policy (see Gates) | `workspace:write` |
| Archive import carrying policies | `create` and `update` (without them the archive imports and its policies are skipped, each skip written to the audit log); an import that would delete existing policies needs `delete`, and `update` as well to remove an active blocking policy of the branch it writes | - |
| Branch merge that adds, changes or deletes a policy | `create`, `update` or `delete` for what it changes, and `update` for a weakening of a blocking policy (see Gates) | - |
| Override a blocking gate | `update` (with a reason) | `workspace:write` |
| Release cut from a branch or tenant, tier1 tenant, ephemeral or sandbox push, release deploy | none: this is deployment, not authoring | - |
| `release push` (a release built from files), or a release archive upload that carries policies | `create` and `update` to carry its policy files; without them `release push` carries the workspace's live-branch policies instead (naming the files in `policies_skipped` when they differ) and an archive upload is refused | - |
| Any export or import while the `policies` feature is off | none: exports omit policies; a push leaves its policy files out and names them in `policies_skipped`, and an archive import leaves its policies out (each audited as `policy:import_skipped`); the workspace's own policies are never changed, and a replace deletes only those of the branches it removes | - |

`workspace:policy` is a level set on a Metadata API access token and on a role's "Workspace Policies" permission; a per-workspace override on a member wins over the role. Both must allow the operation. A token created before policies existed carries no `workspace:policy` level, so it reads nothing until it is reissued. An OAuth token has no per-permission levels: `workspace:read` or `workspace:write` is its ceiling, and the role's permission decides the rest.

Who can author: whoever holds the `workspace:policy` permission at create, update or delete level. A role grants it like any other permission, custom roles included; a role that grants only `read` can read policies and run checks but cannot change them, and reissuing a token does not change that.

Evaluate needs only `read`, so a reviewer or a CI credential can run checks. Storing the run is a write: from a read-only session, or an OAuth token without `workspace:write`, the evaluation returns its findings with `stored: false` and run id `0`, and the retained runs are untouched.

A policy file that is identical to the stored policy needs no write permission in a push: it is reported `unchanged` and skipped. A policy file that differs, pushed by a caller whose `workspace:policy` permission does not allow that change, refuses the whole push before anything is imported, naming the policy keys (`policy_permission_required` or `policy_scope_required`, with `payload.policies`). Exclude the policy files (`xano workspace push -e "policies/*"`) or pull again to push the rest.

What a policy reader can see: a finding names the object it is about - its type, name and id - and says where in the stack the problem is, for any object on the branch. `workspace:policy` read therefore shows object names and ids across the branch even to a role with no access to, say, the database or that API group. The credential check never prints the literal it matched; it names the SHA-256 fingerprint instead. A rule's `allowed_secrets` lists the fingerprints (`sha256:` and 64 lowercase hex digits, e.g. from `printf %s "$VALUE" | shasum -a 256`, or copied from the finding) of values the owner reviewed, and the check skips them wherever it looks. A policy never holds the value itself: any other entry is refused, naming only its position, and an entry that allows nothing is a rule warning. Allowing a secret weakens the policy, so an agent adds one only when the user asks. A gate refusal lists its blocking findings only to a caller who holds `workspace:policy` read; anyone else gets the counts, the run id and, in its message, the keys of the policies they come from.

A `workspace push` (or upload-URL import) by a caller without `workspace:policy` read is evaluated as anyone's is, and the run is stored, but its `policy_check` tells that caller only their own findings on the objects the push carried that they may read (a push that carries the workspace document carries the workspace object too, listed to a caller with `workspace:settings` read), trimmed as an object's coverage is: `{status, message, blocking, run_id: 0, access: "coverage", scope: "pushed_objects", findings, blocking_findings, elsewhere {total, blocking, basis}, results: [], counts {findings, blocking, errors}, total, truncated, note}`. Each finding is `{id, policy_key, policy_title, rule_title, message, blocking, deleted, object, check {label, description, fix_hint} or null}`. The counts are about those findings, except `counts.errors`, the branch's rules that could not run. `elsewhere` counts, never names, the findings on the objects it does not list: with `basis: "introduced"`, those the push introduced (on the live branch, not in the push gate's own evaluation of the branch just before the push; on any other branch, not in the branch's newest run just before the push, while that run still described the branch); with `basis: "all"`, when no such baseline was known, every finding there, existing ones included. Which objects are theirs follows the coverage rule (see Permissions), a trigger by its `obj_type`. `blocking` is what a reader's push of the same change says (the branch holds a blocking finding after it), so the CLI exits 2 for the same push whoever made it, even with nothing of theirs listed; `status` is `fail` when anything is listed, `elsewhere.total` is above 0 or `blocking` is true, else `error` when a rule errored, else `pass`. An older platform answers such a caller `forbidden` and evaluates nothing.

Policy text stays behind this permission. Git sync carries no policies: it leaves the policy files out of the repository, and its commit message says how many. The workspace audit log names each policy change by the policy's identity (id, key, title, version, active, enforcement, actor and action), never its document or source, which live in Version History behind policy read. Request history follows the same line: for a viewer without `workspace:policy` read (or while the policies feature is off), a Metadata API call that carries policy details (a policy route, the object coverage route included, a policy refusal, a push's `policy_check`, a policy document) shows `Hidden: this call carries policy details, which need workspace:policy read.` as its whole input and output. An endpoint's own request history is never masked.

Policies are saved directly, not drafted. `active = false` makes a policy inactive; it does not create a draft. New authored source and structured saves refuse `lifecycle` with `policy: "lifecycle" was replaced by "active"; write active = true or active = false.` Source refusals include the line and column. Stored/imported legacy policies are migrated (`draft` becomes `active: false`); explicit boolean `active` takes precedence. An active policy needs at least one rule; set `active = false` instead to save one without rules.
